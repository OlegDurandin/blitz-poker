# Профиль и прогресс 3.2

## Принятое решение

Владелец уточнил объём после аудита: профиль сначала накапливает сетевые
результаты, затем также принимает статистику по завершении локальной игры.
Реализованы оба пути. Клиентские отчёты разрешены этим уточнением и явно имеют
источник `local`; сетевые итоги имеют источник `server`. Есть общая статистика
и фильтр источника, а внутри каждого — Solo/Duel/Table. Это личный прогресс,
не публичный рейтинг. Старые правила движка и сетевой протокол не менялись.

## Данные и надёжность

SQLite user_version=3. Аддитивная транзакционная миграция сохраняет rooms, tables,
duels. Случайный строковый player_id связан с уникальной парой provider + внешний
ID как TEXT и старым игровым ID. Числа VK и TG не смешиваются; guests не получают
постоянного профиля. Большие игровые ID не передаются в UI как JS Number.

player_results — неизменяемая запись результата для одного участника и одновременно
ledger XP: ключ `(event_id, player_id)` уникален, начисление хранится в этой записи.
Статистика вычисляется из этих записей; отдельной изменяемой копии счётчиков нет.
player_achievements хранит однократные достижения и дату; progress_commits защищает
общий серверный match_id и старый счёт пары от повторного начисления.

Сохранение терминального снимка, счёта дуэли, результатов участников, XP,
достижений и событий выполняется одной SQLite-транзакцией. При ошибке запись
повторяется таймером; новые игровые команды до успешной записи отложены, чтобы
реванш не затёр результат. До подтверждения UI не показывает выдуманные XP.
После аварийного завершения процесса возобновляется последний принятый на диск
снимок. Это сохраняет прежнюю модель сохранения игры, а не вводит WAL команд.

События match_completed, xp_awarded, achievement_unlocked сохраняются в outbox
в транзакции результата и затем пишутся в диагностический лог с event_key.
При падении между логом и удалением из outbox возможен повтор того же event_key;
будущий внешний транспорт должен дедуплицировать этот ключ. Внешний транспорт
аналитики пока не подключён. Скрытых карт и платформенных токенов в событиях нет.

Новые результаты переживают реванши и очистку старых комнат. Старые финальные
снимки при миграции помечаются уже обработанными: backfill и XP за прошлые игры
не выполняются. Старые активные матчи продолжаются и получают новый результат
при завершении. Повреждённые снимки не превращаются в результаты.

## Локальные игры

Новый Solo или локальный стол сохраняет ключ запускающего аккаунта в метаданных.
При завершении итог сначала помещается в localStorage под отдельным ключом для
этого аккаунта и match_id, затем отправляется POST. После подтверждения запись
очереди удаляется. Retry выполняется при открытии приложения/профиля/результата,
событиях online/focus и каждые 30 секунд. Перезапуск WebView очередь не удаляет.
Отдельные ключи матчей исключают потерю соседних записей при записи из двух вкладок.
Повторная отправка после потерянного ответа возвращает первоначальную запись.
Результаты предыдущего аккаунта не отправляются в профиль текущего.

При ошибке записи очереди контроллер пытается сохранить завершённый снимок,
показывает ошибку и допускает retry. Матчи из старых сохранений без владельца,
обучение и прерванные локальные игры не импортируются. В браузерном гостевом
режиме локальная статистика остаётся на устройстве как раньше.

Сервер проверяет поля отчёта, режим, диапазоны чисел, длины и состав, но не
переигрывает локальную партию: её исход сообщает клиент. Такой результат не
является доказательством честной игры. Произвольный player_id/source сервер
не принимает; владельца определяет Bearer-сессия. Локальный Duel отправлять
нельзя. Лимит POST — 4 KiB и 60 запросов на игрока в минуту.

Дата в истории и UTC-день начисления определяются временем приёма сервером.
Отложенная отправка не задним числом меняет XP прошлого дня. Потеря/очистка
localStorage до отправки теряет ещё не принятые локальные результаты.

## Правила прогресса

- Нулевой win-rate — null / «—»; ничья входит в знаменатель.
- Ничья сохраняет серию, поражение обнуляет; серии считают матчи.
- Table классифицируется по начальному составу 3–4 места; два оставшихся
  участника не превращают Table в Duel. Два человека без ботов — Duel;
  один человек + один бот — Solo даже через сетевой Table API.
- Для Table исход берётся из places: единственное первое — победа, несколько
  первых — ничья для этих мест, остальные — поражение. Закрытие без результата
  не начисляет награду; допустимый forfeit дуэли следует результату движка.
- Число раздач матча хранится отдельно от участия: для сетевого Table статистика
  раздач участника считается по его проекциям с выданными ему картами.
- Лучшая комбинация — только существующий серверный BestShown, пять карт со
  вскрытия. Для локальных отчётов этот рекорд не заявляется.
- XP по умолчанию Solo 10 + 5 за победу; Duel/Table 20 + 10. Бот-лимит 100 XP
  за UTC-день, общий 300. Смешанные столы и все локальные игры входят в бот-лимит.
  Статистика продолжает расти после достижения лимита.
- Уровни вычисляются сервером по 100*(N-1)*N/2, с целочисленной арифметикой.
- Достижения: первый матч, первая победа, 10 матчей, серия из трёх побед.

Настройки в окружении сервера (валидируются при запуске, 0…1000000):
`PROFILE_XP_SOLO`, `PROFILE_XP_SOLO_WIN`, `PROFILE_XP_MULTIPLAYER`,
`PROFILE_XP_MULTIPLAYER_WIN`, `PROFILE_XP_BOT_DAILY`, `PROFILE_XP_DAILY`.
Пример добавлен в `crates/pvp-server/.env.example`. Рабочий `.env` не изменён.

## API и UI

Все маршруты требуют проверенную платформенную Bearer-сессию `/api/auth`.
GET `/api/me/profile?source=all|server|local` возвращает профиль, готовый уровень,
статистику, достижения и последние матчи. GET `/api/me/matches` принимает
source, mode=all|solo|duel|table, limit=1…20 и cursor; порядок по серверной дате
и event_id, последние сверху. GET `/api/me/matches/{event_id}` проверяет участника
и возвращает только его проекции раздач. Перечень матчей не содержит карт.
POST `/api/me/local-results` принимает match_id, mode, outcome, final_stack,
hands_played, hands_won, opponents; повторный ключ не меняет первый результат.

Профиль открывается с главного экрана и результата; работающая сетевая связь
при открытии профиля сохраняется. Есть загрузка, ошибка с retry, нулевое состояние,
фильтры, карточка матча, пагинация и доступные состояния достижений.
История/replay Solo по старой кнопке остаётся доступна. Новый список профиля
показывает факты матчей; новый replay столов не добавлен.

## Проверки и ограничения

Финальные проверки:

- `cargo test -p pvp-server --release --lib`: 52 passed.
- `cargo test -p pvp-server --release --test duel`: 14 passed, включая
  профили VK/TG с одинаковыми внешними ID, результаты обоих участников,
  сохранение истории после реванша, restart и приватность HTTP API.
- `npm --prefix web test`: 74 passed, 1 skipped, 13 файлов.
- `npm --prefix web run build`: успешно, включая WASM, TypeScript и Vite.
- `cargo fmt --all -- --check` и `git diff --check`: успешно.
- Исходные тесты неизменённых poker-core, bot и poker-wasm прошли при аудите;
  повторный полный турнирный прогон ботов после UI-изменений не выполнялся.

В Chrome вручную
проверены пустой профиль, заполненный профиль с 23 тестовыми локальными матчами,
пагинация 20+3, карточка результата с достигнутым лимитом, открытие/закрытие,
переключение режима, ширины 320/375/430 px. Снимки осмотрены через Computer Use.
Использовалась отдельная SQLite в /tmp и dev-аккаунт 901; production не затронут.
Реальные WebView VK/TG, их safe areas и системный увеличенный шрифт требуют
проверки на устройствах. Полные платформенные E2E не заявляются выполненными.

Агрегация сейчас читает журнал игрока на сервере. При большой истории нужно
измерить нагрузку и добавить восстанавливаемую projection; клиент получает
историю только страницами. Unique human opponents пока не выводится.
Длительность матча пока не включена в продуктовые серверные события.

Перед применением к production нужна резервная копия SQLite. Откат старого
бинарника поверх v3 не поддерживает новый журнал; откатывать следует вместе
с резервной копией БД. Миграция новой более неизвестной версии отклоняется.
Коммиты и деплой в рамках этой работы не выполняются.
