# Blitz Poker 3.2 — аудит профиля и прогресса

Принятое после аудита решение владельца: сначала серверный профиль для сетевых
режимов, затем отправка итогов локальных игр для накопления в том же профиле.
Это разрешает клиентские отчёты: они помечаются `local`, отдельно от подтверждённых
`server`. Пункты ниже описывают исходное состояние до реализации; актуальное
описание находится в `docs/profile-progress-3.2.md`. Остановка из §4 больше
не блокирует работу после этого решения.

Дата: 13 ноября 2026. Исходный commit: `77aefd0`.
Основание: `BLITZ-POKER-3.2-PROFILE-PROGRESS-CODEX.md` из Downloads.
Это аудит и проект изменений; миграции и функциональность 3.2 ещё не реализованы.

## 1. Что уже существует

| Область | Реализация и источник истины | Что переживает перезапуск |
| --- | --- | --- |
| Solo | `web/src/game/useGame.ts`, Rust `Match` через `poker-wasm` | Снимок, локальные счётчики и до 30 матчей с раздачами в localStorage этого WebView |
| Локальный стол с ботами | `useTableGame.ts`, `tableStorage.ts`, Rust `Table` через WASM | Незавершённый стол и счётчики мест; отдельного архива завершённых столов нет |
| Сетевая дуэль | `room.rs`, `hub.rs`, серверный `Match` | SQLite `rooms`: последний снимок комнаты; `duels`: агрегированный счёт пары |
| Сетевой стол | `table_room.rs`, серверный `Table` | SQLite `tables`: последний снимок стола |
| Авторизация | `server.rs::identify`, `vk.rs`, `telegram.rs`, `auth.rs::Sessions` | Идентичность воспроизводится при повторном входе; сессии 12 часов и одноразовые WS tickets находятся в памяти |

Стек: Cargo workspace из `poker-core`, `bot`, `poker-wasm`, `pvp-server`; axum 0.8,
rusqlite/SQLite, React 19 + TypeScript + Vite. README описывает развитие проекта:
ранний раздел «всё в localStorage» относится к локальной игре, не к сетевым режимам.
Файлов AGENTS.md в репозитории не найдено. `.env` не читался и не изменялся.

SQLite использует WAL, `synchronous=NORMAL`, DDL через `CREATE TABLE IF NOT EXISTS`.
`store.rs::SCHEMA` безусловно устанавливает `PRAGMA user_version = 2`;
последовательного мигратора нет. Персональных HTTP API пока нет:
есть `/api/auth`, `/api/ticket`, `/ws`, `/health`.

## 2. Завершение и история

Дуэль: `Room::after_transition → finish` получает `MatchResult` из движка,
обновляет счёт комнаты и создаёт неперсистентный `Event::MatchFinished`.
`Hub::commit` забирает события, сохраняет комнату, затем отдельно вызывает
`Store::record_duel`. Это не одна транзакция; событие теряется при ошибке записи,
а агрегат пары не имеет уникального match_id. Для XP этот путь переиспользовать
без усиления надёжности нельзя.

Стол: `TableRoom::after_transition` при `Phase::MatchOver` создаёт
`TableEvent::Finished { people, bots }`; `commit_table` считает метрики и сохраняет
снимок. Отдельной записи результата нет. Реванш заменяет `game` новым матчем
как у дуэли, так и у стола. Закрытые комнаты/столы могут удаляться через
`prune_closed`. Поэтому снимки не являются долговечным полным архивом матчей.

Достоверный итог дуэли: `MatchResult.outcome`, с инверсией для второго места.
Сдача/таймаут/disconnect после grace оформляются движком как `forfeit`, а не
угадываются по стеку. Это допустимый существующий терминальный результат.
Стол: `TableResult.places` уже учитывает стеки, выбывание и порядок ухода;
места могут совпадать. Проектируемое отображение: единственное первое место —
победа, разделённое первое — ничья для разделивших, остальные — поражение.
Нельзя брать победителя последнего банка или только максимальный стек.
Закрытый стол без `MatchOver` и `result` не даёт матч, победу или XP.
`ended_early` само по себе не означает техническую ошибку.

Оба движка уже сохраняют лучшие комбинации со вскрытия:
`MatchResult.best_hand/opponent_best_hand` и `TableResult.best_hands` с пятью
картами (`BestShown`). Новый evaluator не нужен. Сравнение силы следует
переиспользовать из Rust, не сравнивать текстовые названия категорий.
Раздачи и выигранные руки можно брать из результата и серверной истории;
в столах `hands_won` означает единоличный выигрыш основного банка.

Приватную историю проецировать существующими `Match::hand_records` и
`TableHandSummary::record_for` для авторизованного места. Сырые снимки содержат
закрытые данные и не должны уходить в API. Клиентские History/Replay сейчас
работают с локальным архивом Solo; готового серверного API истории нет.
Для стола достаточно карточки фактов без обещания нового replay.

## 3. Идентичность

`player.rs::PlayerId` — u64 с непересекающимися диапазонами VK, TG и Guest.
VK 123 и TG 123 уже различаются, имена/аватары ID не меняют. Но ID зависит от
провайдера и не является требуемым независимым profile player_id. Связки VK↔TG
нет. TG identity проверяется HMAC initData, VK — подписью launch parameters.
Имя/фото TG берутся из подписанных данных, VK — из очищенных клиентских полей.

Предлагается добавить отдельный случайный строковый profile player_id и таблицу
identity `(provider, provider_user_id TEXT UNIQUE в паре с provider)` с привязкой
к прежнему сетевому PlayerId. Существующие игровые ID, SQLite JSON и WS-протокол
оставить совместимыми. Большие сетевые ID не пересылать в новый UI как JS Number.
Провайдер в новом контракте — `vk|telegram`; внутреннее `tg` нормализовать.
Профили VK и TG раздельные, автоматического merge нет.
Guests продолжают играть, но не получают постоянный платформенный профиль 3.2.

Существующие сессии можно расширить безопасным read-only получением Profile по
Bearer token: сейчас Sessions предоставляет ticket/redeem, но не lookup для GET.
`/api/me/*` всегда определяет участника из сессии и проверяет его участие в матче.
Ни query player_id, ни знание match_id не дают права читать историю.
Клиентскую авторизацию нужно вынести из private session внутри DuelConnection
в общий сервис: сейчас useDuel включается только на сетевых экранах.

## 4. Решение, необходимое до реализации

Solo и локальный Table не отправляют действия или результаты серверу. Клиент
контролирует WASM-снимок, localStorage, колоду и итог. Авторизация пользователя
не делает присланный им результат достоверным. Приём `outcome/final_stack` через
POST и дневные лимиты не выполнят требование серверного источника истины.

| Вариант | Изменения | Риск и результат |
| --- | --- | --- |
| A — серверные Solo и столы с ботами | Сервер создаёт матч и колоду, принимает действия, запускает существующего бота; клиент отображает проекции. Используются прежние правила Rust | Рекомендуется для полного 3.2. Существенная смена пути исполнения Solo, зависимость от сети, нужны reconnect/latency E2E и решение о судьбе офлайн-игры |
| B — сначала прогресс сетевых режимов | Новый журнал и профиль только для авторитетных дуэлей и сетевых столов; локальная история сохраняется отдельно | Ниже риск, но неполный 3.2: локальный Solo и Table не начисляют серверные XP/статистику; нужна явная маркировка ограничения |
| C — серверная проверка локальной игры | Сервер выдаёт исходное состояние, хранит его, повторяет журнал действий и проверяет бота | Высокий риск: синхронизация версий/RNG, защита от повторного выбора исходов. Раскрытие клиенту полной колоды остаётся проблемой. Не рекомендуется как быстрый путь |

По §12 ТЗ работа остановлена после аудита: полное выполнение требует изменения
существующего пути игровой обработки. В этом изменении нет переноса режимов,
нового протокола, миграций БД или начисления клиентских XP.

## 5. Проект модели и миграций после выбора варианта

1. Заменить безусловный user_version=2 версионным мигратором в транзакции;
   принимать существующую v2, создавать новую схему при пустой БД и отклонять
   неизвестную более новую версию. Протестировать копию v2 с активными комнатами.
2. Аддитивно создать players, platform_identities, immutable match_results и
   match_participants. Участники фиксируют identity, место, исход, стеки и snapshot
   имён/ботов; состав и режим фиксируются на старте, не меняются при уходе игроков.
   Текущий Table API допускает два места: 2 человека без ботов → duel,
   1 человек + бот → solo, 3–4 места → table независимо от состава к финалу.
3. Создать xp_ledger с UNIQUE(match_id, player_id, reward_kind), achievements с
   UNIQUE(player_id, achievement_key), индексы истории
   `(player_id, finished_at, match_id)` и дневного XP. Для MVP счётчики вычислять
   из журнала, избегая второго источника истины. При необходимости projection
   восстанавливается упорядоченным replay результатов.
4. В одной SQLite-транзакции сохранять терминальный снимок и вставлять результат,
   ledger, достижения, обновлять существующий счёт пары только при первой вставке
   match_id. Публиковать подтверждение и события после commit. При ошибке хранить
   незавершённую запись для retry и не позволять реваншу затереть её; при рестарте
   сверять терминальные снимки с журналом. Нужны тесты с ошибками между шагами.
5. Новый API: GET `/api/me/profile`, `/api/me/matches`,
   `/api/me/matches/{match_id}`. Курсор `(finished_at, match_id)`, последние сверху,
   20 по умолчанию, ограниченный limit, проверка mode/cursor и привязки участника.
   Read API не начисляет награды. Старые сетевые клиенты продолжают работать.

Старые снимки сохраняются без переписывания. Локальные архивы не импортируются
как подтверждённые сервером результаты. Агрегат `duels` нельзя превратить в
историю отдельных матчей. По умолчанию backfill отключён и XP начинается с 3.2;
показывать «Статистика ведётся с обновления 3.2». Опциональный backfill только
терминальных доступных снимков — отдельная идемпотентная процедура без старых XP,
после проверки согласованности результата и участников. Аудит исследует исходники,
не содержимое production SQLite; полнота реальных старых записей неизвестна.

Обратная совместимость: новые таблицы не удаляют rooms/tables/duels/localStorage;
старые активные матчи завершаются по прежним правилам. Перед реальным применением
нужны backup БД и тест восстановления. После включения журнала откат на старый
writer требует отключения прогресса или последующей сверки: сам по себе старый
бинарник новый журнал поддерживать не будет.

## 6. Зафиксированные правила для следующего этапа

- win_rate = wins / (wins + losses + draws); при нуле возвращать null/«—».
- Ничья сохраняет серию, поражение сбрасывает. Серии all и каждого режима
  считаются по завершённым матчам в стабильном порядке, не по раздачам.
- XP конфиг сервера: Solo 10+5 за победу, Duel/Table 20+10; ничья без бонуса.
  Бот-матч для лимита — любой матч с bot_count > 0, включая смешанные столы.
  Дневные потолки 100 bot XP и 300 общего XP, по UTC времени серверного завершения;
  фактическая награда — минимум запрошенного XP и обоих доступных остатков.
  Лимиты не ограничивают статистику. Конфигурацию награды фиксировать в ledger.
- level = максимальный N с 100*(N-1)*N/2 <= xp_total; расчёт с защитой от
  переполнения на сервере, UI получает готовый уровень и прогресс.
- Достижения first_match, first_win, ten_matches, three_win_streak — серверные,
  единожды; unlocked_at сохраняется. Unique opponents возможен для новых
  участников с profile player_id; исторические неполные данные не восстанавливать.
- Аналитику profile_opened/profile_mode_selected добавить к существующему
  `game/analytics.ts`; транспорт пока не подключён. Серверные match_completed,
  xp_awarded, achievement_unlocked создавать только при первой записи журнала;
  для надёжной внешней доставки нужен outbox и дедупликация event_key у получателя.
  Не писать initData, токены, сырые снимки или скрытые карты в логи.

## 7. Этапы и приёмка

После выбора A/B/C: сначала модель/миграции и тесты границ XP, серий, ничьих,
классификации состава; затем серверный журнал/API с повторным завершением,
рестартом, двумя устройствами, ошибкой SQLite и проверкой чужой истории.
Далее UI профиля, пагинация, фильтры, loading/empty/error и подтверждённые XP в
результате. Финальный этап — VK/TG E2E, 320/375/430 px, safe areas, увеличенный
шрифт, reconnect и совместимость старых сохранений. Правила покера и replay
переиспользуются. Коммиты и деплой не выполняются без отдельного запроса.
